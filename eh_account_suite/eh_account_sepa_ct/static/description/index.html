The purpose

Make the next finance decision clearer.

SEPA Credit Transfer builds ISO 20022 credit-transfer files for posted vendor-payment batches. Each batch explicitly opts into SEPA controls; merely configuring an originator never changes ordinary outbound batches. PAIN.001.001.09 is the default for new originators, while .03 remains available for banks that still require it.

Inside this module

Built around the work your team does.

Caught before the bank

IBAN passes a pure Python mod-97 check, country in the SEPA zone with the exact per country length, and BIC against ISO 9362 structure. No external library. A bad account never reaches the file.

The file your bank actually wants

Pick PAIN.001.001.03 (legacy SEPA rulebook) or PAIN.001.001.09 (current EU Implementation Guidelines, 2024 onward) per originator. The .09 path renames BIC to BICFI automatically so the same batch serves either bank.

Every file accounted for

Each export records user, timestamp, message ID, transaction count, control sum and SHA-256. A second live instruction is blocked until a manager voids the unsent file for re-cut, preserving every audit row.

MIXED CURRENCY

A batch that mixes currencies is refused before any file is written, with the offending currency names listed, rather than silently truncating to one currency.

BANK ACCOUNT RESOLUTION

Every payment must name one active, outgoing-payment-verified bank account owned by that payment's commercial counterparty. Export never guesses a first partner bank or crosses company boundaries.

MSGID COLLISION

Two exports in the same UTC second still get distinct 35 character message IDs via a uuid fragment, with the name part capped so the uuid can never be truncated away.

OUT OF ZONE IBAN

The IBAN country must be in the embedded SEPA zone registry and match the exact per country length before mod-97 runs, so an out of zone or wrong length IBAN is rejected with a specific message instead of a generic failure.

ACCENTED NAMES

Supplier names and remittance text are transliterated and stripped to the SEPA Latin character set, so accented or non Latin text does not break the file at the bank gateway.

Worked operating scenario

The clerk enables SEPA Credit Transfer, posts the supplier payments, and generates the file. One selected supplier bank IBAN is one digit short; generation stops and names that payment before any export row exists. The clerk fixes and verifies the explicit bank target, then retries. A supplier name carries an accented character, which the SEPA Latin pass transliterates so the gateway accepts it. The originator is set to PAIN.001.001.09, so the file carries BICFI as this bank now requires. The generated export shows the message ID, thirty transactions, quantised control sum and SHA-256. The clerk downloads the verified XML, uploads it to the bank portal, and only that request moves the export to downloaded. One pay run, one file, no surprises at the gateway.

Workflow reference

Understand the records and controls.

Capability detail 1

Validation happens before the file is written, not after the bank rejects it. IBAN is checked with a pure Python mod-97 (ISO 13616) routine that also verifies the country is in the SEPA zone and the length matches that country exactly. BIC is checked against ISO 9362 structure rules, with 8 character codes padded to 11 with the XXX branch. There is no external validation library to install. If a batch mixes currencies, generation refuses and names the offending currencies so you split the batch before the bank does.

Capability detail 2

Names and remittance text are run through a SEPA Latin character set pass that transliterates accents and strips characters the scheme does not allow, so a supplier name with diacritics does not bounce at the gateway. Each transaction renders as its own entry for cleaner reconciliation on the bank side.

Capability detail 3

Every export writes an immutable audit row with actor, timestamp, message ID, quantised control sum and SHA-256. Generation leaves state at generated; requesting the verified attachment changes it to downloaded. A second live instruction is blocked until a manager explicitly voids the unsent file for re-cut. Two-person maker/checker and stricter three-person policies are configurable per originator.

Capability detail 4

Built directly from the public ISO 20022 specification. Original work, not a derivative. Pairs with the batch payment module: build the batch, generate the SEPA file, upload to the bank.

MISSING ATTACHMENT

Downloading an export whose attachment was deleted raises a clear remediation error instead of a 404, and only flips state to downloaded on success.

Dual PAIN.001 output per originator

Generate PAIN.001.001.03 or PAIN.001.001.09 selected on the journal originator, with the BIC element renamed to BICFI automatically for the .09 version. Output targets the published namespace and structure and carries the ISO 20022 schemaLocation hint.

Pure Python IBAN and BIC validation

Dependency free IBAN mod-97 (ISO 13616) and BIC (ISO 9362) checks, enforced when you save the originator and again when the export is built. IBAN and BIC are canonicalised, spaces stripped, upper cased, 8 character BIC padded to 11, before they are stored.

Single currency enforcement

Mixed currency batches are blocked before generation with the currency names shown, because SEPA requires one currency per file and a single control sum.

Per export audit record

Each generated file gets an export record with the SHA-256 hash, user, timestamp, transaction count and control sum. A second live instruction is blocked until explicit void-for-recut, and state changes from generated to downloaded only when the file is requested.

SEPA Latin sanitisation

Names and remittance information are transliterated and filtered to the characters the SEPA scheme allows, so accented or non Latin text does not break the file at the bank gateway.

Verified by parse-back tests

The test suite renders an inline payload, parses the XML back with lxml, and asserts the namespace, message ID, transaction count, control sum, per transaction amounts and currency, service level (SEPA) and charge bearer (SLEV), element by element.

Sepa ct source fingerprint

SHA-256 of the approved originator, creditor bank accounts, and creditor names. Export recomputes it under row locks and fails closed if any source changed after confirmation.

SEPA Credit Transfer

Explicitly route this outbound batch through SEPA source approval and PAIN.001 export controls. A journal originator alone never changes ordinary non-SEPA batches.

Provenance status

Only exports generated after server-side provenance controls were installed are downloadable. Pre-control rows are retained as audit evidence but quarantined because their origin cannot be proven.

Journal

Bank journal whose IBAN drives the Dbtr block of every PmtInf section. One originator per journal; reuse across every batch sourced from this journal.

Initiating party name

Goes into GrpHdr/InitgPty/Nm. The exact legal name the bank has on file for the account holder. Capped at 70 characters per the scheme.

Initiating partyentifier

Optional identifier for InitgPty/Id/OrgId/Othr/Id. Capped at 35 characters. Used by some banks to verify the file originator against a customer reference.

IBAN

Source IBAN. Validated locally at write time using mod-97 per ISO 13616; the export refuses to render if this fails.

BIC / SWIFT

Optional. When omitted the export emits 'NOTPROVIDED', which signals the bank to look up the BIC from the IBAN. Some banks reject NOTPROVIDED; if yours does, fill this in.

Requested execution offset days

Calendar days to add to the batch Payment date when computing ReqdExctnDt. 0 means same-day and 1 means the next calendar day. The export does not perform business-day adjustment; set the offset to match your bank's processing rules.

Segregation policy

Two-person policy lets confirmer and poster split approval and file generation, but the person who approved the current SEPA source fingerprint still cannot export it. Three-person policy also requires the exporter to differ from both confirmer and poster.

Scope and requirements

Know exactly what you are installing.

Currency is EUR only, fixed by the SEPA scheme. Non EUR transfers are out of scope, use a different transfer instruction.

The file targets the published PAIN.001.001.03 and .09 namespace and structure and carries the schemaLocation hint. It does not bundle an XSD or run xmllint or XSD validation; the tests assert structure by parsing the XML back, not by validating against a schema.

The SHA-256 hash and supersession let an auditor detect a duplicate generation, but the module does not hard block a second export of the same batch.

One message (CstmrCdtTrfInitn) per export, SEPA service level only, charges allocated SLEV, and no batch booking. Each transaction renders as its own entry.

This is a file generator. It does not connect to the bank or transmit the file; you download the XML and upload it through your bank portal.

Standards references describe the accounting subject addressed by the module. They do not establish certification, statutory filing acceptance or suitability for every jurisdiction. Your finance team owns its assumptions, accounting policies and review.

Run one customer-receipt or vendor-payment batch with partial settlement, mixed-currency support on company-currency journals, reviewed recipient banks and an exact pre-post CSV preview.

One bad payment stops the whole run

Posting is atomic. A closed period, invalid payment or reconciliation failure rolls the whole attempt back, leaving every member unposted and the reviewed batch confirmed for correction.

Plain payment underneath

The batch creates and posts standard Odoo payments with only a nullable batch link added. Reconciliation, the vendor ledger, partner follow-ups and reporting already understand the output.

Mandatory two-manager approval

One EH Accounting Manager confirms and freezes the batch. A second, different EH Accounting Manager must post it. This maker-checker separation is intentionally not configurable.

ATOMIC POST

Every member either posts and reconciles successfully or the complete attempt rolls back. The batch remains confirmed when correction is required.

SEALED REVIEW

Confirmation freezes payment inputs and the exact CSV rows. Posting refuses changed or malformed approval evidence.

MIXED COMPANY

The build wizard refuses source documents outside the batch company and validates the journal, direction and currency.

DUPLICATE CLAIM

A source document with a live draft payment claim cannot enter another batch, closing the double-pay and double-collection window.

CONTROLLED REVERSAL

A posted batch is corrected with verified counter-entries. Original posted cash moves and their audit evidence remain immutable.

36-month dormancy

Five signals, shown

Post Dated Cheques (PDC)

Track issued and received post dated cheques as real records with a guarded lifecycle and balanced journal entries on present, clear and bounce.

Real records, real entries

Every cheque is a queryable, exportable, audit-ready record. Presentation uses dedicated direction-specific cheque transit; clearance uses Odoo outstanding accounts until bank reconciliation confirms cash.

The book is the source of truth

Serial allocation takes a Postgres row lock so concurrent registrations queue rather than race, rejects out-of-order serials, and exhausts the book automatically. A unique constraint on book and number is the backstop.

Yours to keep

LGPL-3 source on disk. No activation key, no phone-home, no recurring licence. Bounce reasons are configurable data, not hard-coded enum literals. Read it, extend it, fork it if you need to.

FX · MULTI-CURRENCY

A foreign-currency cheque posts the present, clear and bounce entries by converting the cheque amount into company currency for debit and credit while carrying the signed foreign amount in amount currency, so FX cheques post balanced and stay reconcilable.

EARLY PRESENTATION

A post dated cheque cannot be presented before its value date, because real banks refuse it. No context key bypasses this date gate; opening balances require an explicit audited accounting correction instead of an early presentation.

CONCURRENCY

Registration takes a SELECT FOR UPDATE row lock on the cheque book so two simultaneous registrations queue instead of racing the next-serial pointer, with a unique constraint on book and cheque number as the safety net.

SERIAL GAPS

Registering a serial that is not the book's next number is rejected with a remediation message, preventing out-of-order or skipped cheque numbers.

BOUNCE IDEMPOTENCY

The bounce only posts a reversal when the present move actually exists and is posted, so it never double-reverses and never reverses an unposted entry.
